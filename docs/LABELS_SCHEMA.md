# 라벨 목록 JSON

> **상태: 3판. 승인 후 구현했다** (`modules/labels_io.py`).
> 이 구조는 **앱으로 그대로 넘어간다.** 나중에 바꾸면 앱과 데스크톱이 갈라지므로
> 지금 확정한다.
>
> **2판:** 1판의 id 설계를 실측했더니 **해상도가 바뀌면 깨졌다.** id를 매칭 키로
> 쓰는 것을 그만두고 인식 입력을 300dpi로 고정했다(아래 실측표).
> **3판:** `confidence`를 2값에서 3값으로 넓히고, 정밀도 0%인 `snap_residual`을
> 등급에서 뺐다.

---

## 왜 JSON인가

지금 골든은 TSV다. 그건 "한 글자라도 바뀌면 실패"를 사람이 눈으로 확인하기 좋아서다.
하지만 앱이 쓸 데이터로는 안 맞는다 — 보표·라벨의 중첩 구조가 안 되고,
플래그 배열 같은 것을 표현할 수 없다.

**골든 TSV는 그대로 둔다.** 회귀 테스트용이고 목적이 다르다.

## 필드

### 문서 수준

| 필드 | 뜻 |
|---|---|
| `schema` | 구조 판 번호. **필수.** 앱과 데스크톱이 갈라지는 것을 이걸로 막는다 |
| `generator` | 만든 프로그램과 판 번호. 버그 추적용 |
| `source.file` | 원본 파일명(경로 제외 — 기기마다 다르다) |
| `source.page` | 0부터. PDF가 아니면 0 |
| `source.width/height` | **원본 이미지 픽셀 크기.** 모든 좌표의 기준 |
| `source.dpi` | PDF를 몇 dpi로 펼쳤나. **300 고정**(아래 「해상도를 고정한다」). 다른 값이면 불러올 때 경고한다 |
| `source.sha256` | 원본 파일 해시. 다른 파일에 엉뚱한 라벨을 덮어쓰는 사고를 막는다 |
| `music.key_*` | 조표. `key_letters`는 ♯/♭이 붙는 음이름 순서 |
| `music.tonic` | 으뜸음. 이동도 계산에 쓴다 |
| `music.minor` | 단조 여부. 조표만으로는 판별 불가라 사용자가 지정한다 |
| `music.notation` | `solfege`(고정도) · `solfege-movable`(이동도) · `letter`(음이름) |

### 보표 수준

| 필드 | 뜻 |
|---|---|
| `id` | 보표 번호. 위에서부터 0, 1, 2… |
| `clef` | `treble` · `bass` |
| `line_ys` | **오선 5줄의 y좌표.** 앱이 라벨을 다시 그릴 때 필요 |
| `spacing` | 오선 간격(px). 모든 크기 계산의 단위 |
| `top` / `bottom` | `line_ys[0]`, `line_ys[4]`. 편의용 중복이지만 앱 코드가 단순해진다 |

### 라벨 수준

| 필드 | 뜻 |
|---|---|
| `id` | 사람이 읽는 식별자. 한 파일 안에서 유일하다. **매칭 키로 쓰지 않는다** — 아래 참고 |
| `staff` | 소속 보표 id |
| `x` / `y` | **원본 이미지 픽셀.** 앱은 화면 크기가 다르니 그릴 때 변환한다 |
| `nx` | `x / spacing`. **오선 간격 단위 가로 위치.** 불러오기 매칭의 기준값 — 픽셀과 달리 확대·축소에 안 흔들린다 |
| `pitch` | 실제 음. `"C#4"` 꼴. 옥타브는 과학적 표기(가온다 = C4) |
| `step` | 오선 맨 아랫줄 기준 반칸 단위 정수. 위로 갈수록 +. **음고의 원본이자 매칭의 1차 키.** 실측에서 가장 안정적이었다(98~99%) |
| `accidental` | `"#"` · `"b"` · `"natural"` · `null`. 그 음표에 실제로 붙은 임시표 |
| `text` | **표기된 계이름.** `notation`에 따라 달라진다 |
| `confidence` | `certain` · `caution` · `check`. **값만 있고 색은 없다** — 아래 「확신도」 |
| `flags` | 걸린 조건 이름 배열. 빈 배열이면 아무것도 안 걸림 |
| `edited` | 사용자가 고쳤는가. `true`면 재인식해도 덮어쓰지 않는다 |

---

## pitch와 text를 왜 나누나

`text`만 있으면 **고정도 ↔ 이동도 전환을 재계산할 수 없다.**
`pitch`(또는 `step` + `accidental`)가 있어야 앱에서 표기법을 바꿀 때
다시 인식하지 않고 계산만으로 처리한다.

반대로 `pitch`만 두고 `text`를 매번 계산하지 않는 이유는, 사용자가 계이름을 직접
고칠 수 있어야 하기 때문이다(`edited: true`). 그때는 `text`가 원본이 된다.

## id를 어떻게 안정시키나

**요구사항:** 재실행해도 같은 음표는 같은 id여야 사용자 수정이 유지된다.

**좌표 해시는 안 된다.** 검출 좌표는 알고리즘을 고치거나 이미지를 다시 렌더링하면
1~3px 흔들린다. 원시 좌표로 해시하면 그때마다 id가 전부 바뀐다.

### 1판의 안: 음악적 좌표를 양자화한다

```
id = "s{staff}-p{step}-x{round(x / spacing * 2)}"
```

가로 위치를 반칸 단위로 양자화하면 ±0.25sp 흔들림까지 흡수한다고 봤다.
**재 봤더니 절반만 맞았다.**

### 실측 1 — 중복과 재실행: 통과

악보 10쪽 2714개 라벨 전부에 id를 매겨 봤다.

| 악보 | 라벨 | 고유 id | 중복 |
|---|---:|---:|---:|
| 쇼팽 D♭ 1~6쪽 | 1818 | 1818 | **0** |
| 바흐 미뉴에트 | 185 | 185 | **0** |
| RE:Aoharu 1~3쪽 | 711 | 711 | **0** |

같은 입력을 두 번 돌린 결과도 **완전히 일치**했다.
**요구사항 그 자체("재실행해도 같은 id")는 만족한다.**

### 실측 2 — 해상도가 바뀌면 깨진다

앱은 자기 해상도로 PDF를 펼친다. 그래서 300dpi로 만든 라벨을 다른 dpi에서
이어받을 수 있어야 한다고 보고, 같은 페이지를 다른 dpi로 펼쳐 비교했다.

**기하학적으로 같은 음표끼리 먼저 짝지은 뒤** 조각별 일치율을 셌다 —
그래야 "인식이 달라진 것"과 "id 공식이 흔들리는 것"이 안 섞인다.

| 비교 | 짝지어짐 | `step` 일치 | id 완전 일치 |
|---|---:|---:|---:|
| 쇼팽 1쪽 300 vs 400dpi | 182 / 240 | 179 (**98%**) | 82 (**45%**) |
| 쇼팽 1쪽 300 vs 320dpi | 174 / 240 | 160 (**92%**) | 115 (**66%**) |
| 바흐 300 vs 400dpi | 147 / 185 | 145 (**99%**) | 79 (**54%**) |

읽는 법이 셋이다.

1. **`step`은 안정적이다(92~99%).** 음악적 좌표라는 발상 자체는 맞았다
2. **가로 양자화가 깨진다.** 차이 분포가 `{-1: 57, 0: 83, 1: 36, 2: 6}` —
   대부분 ±1이다. **양자화 경계에 걸린 음표는 어떤 칸 크기를 써도 흔들린다.**
   칸을 키우면 경계 사고는 줄지만 서로 다른 음표가 같은 칸에 들어간다
3. **더 큰 문제 — 인식 자체가 해상도 간에 24% 어긋난다.** 240 → 236(400dpi),
   240 → **274**(320dpi), 바흐 185 → 170. 짝을 아예 못 찾은 것이 58/240이다.
   **id를 어떻게 설계해도 이건 못 고친다**

600dpi에서는 오선 그룹핑이 아예 실패했다(`StaffNotFoundError`).
검출 문턱값이 300dpi 실측으로 유도된 값이라 그렇다.

### 결정 1 — 인식 입력 해상도를 300dpi로 고정한다

**"현재 300dpi에서만 검증됨"이 아니다. 다른 해상도에서는 인식이 실패하거나
결과가 달라진다.** 실측이 근거다.

| 해상도 | 무슨 일이 일어나는가 |
|---|---|
| 400dpi | 같은 페이지인데 **짝을 못 찾은 라벨 58 / 240** (240 → 236개로 검출 자체가 달라짐) |
| 320dpi | 240 → **274개**. 34개가 더 잡힌다 |
| 600dpi | **`StaffNotFoundError`** — 오선 그룹핑 단계에서 죽는다 |

파이프라인의 문턱값은 전부 300dpi 이미지에서 재서 나왔다(`docs/COLLAB.md` §1).
`LEDGER_RUN_SP = 1.30sp` 같은 값이 sp 단위라 해상도에 중립적으로 보이지만,
검출 이전의 이진화·형태학 연산은 **픽셀 단위**라 그렇지 않다.

- PDF는 항상 `pdf_dpi=300`으로 펼친다. 앱도 같다
- `source.dpi`에 기록한다. 다른 값이면 **불러오기를 막고 사용자에게 선택시킨다**
  (아래 「dpi 불일치는 조용한 경고가 아니다」)
- 화면 확대·축소는 **그릴 때만** 한다. 인식 입력은 건드리지 않는다

### dpi 불일치는 조용한 경고가 아니다

로그 한 줄짜리 warning으로 두면 아무도 안 본다. 그런데 이 경우 **라벨이 통째로
어긋난다** — 사용자가 고친 것이 절반쯤 사라지고, 원인은 나중에 찾기 어렵다.

- 불러오기를 **중단**하고, 무엇이 다른지(저장 300 / 현재 400) 화면에 띄운다
- 사용자가 고르게 한다: **300dpi로 다시 인식** / **그래도 강행**(수정이 사라질 수 있음을 명시)
- 강행을 고르면 결과에 `dpi_mismatch: true`를 남긴다. 나중에 원인을 추적할 수 있어야 한다

### 결정 2 — id는 매칭 키가 아니다

id는 파일 안에서 사람이 읽고 가리키기 위한 이름으로만 둔다.
**불러오기는 좌표 매칭으로 한다.**

```
같은 staff · 같은 step · |Δnx| < 0.5  중에서
가까운 순으로 그리디 1:1 매칭
```

`step`이 다르면 **붙이지 않는다.** 못 붙은 저장 라벨은 `orphan`으로 **보고한다** —
조용히 버리면 사용자 수정이 사라진 것을 아무도 모른다.

#### 상한 0.5sp는 어디서 나왔나

**위에서 아래로 눌린 값이다.** 같은 높이(`step`)의 두 음표는 머리가 겹칠 수 없으므로
최소한 머리 폭만큼 떨어져 있다. 실측 최소 간격은 이랬다.

| 악보 | 같은 `staff`·`step` 이웃 최소 간격 |
|---|---:|
| 쇼팽 D♭ 1쪽 | 1.77sp |
| 쇼팽 D♭ 3쪽 | 1.33sp |
| 바흐 미뉴에트 | **1.30sp** |

가장 좁은 것이 1.30sp다. 이는 음표 머리 폭(1.2sp, 958개 실측)과 일치한다 —
**우연이 아니라 물리적 바닥이다.** 두 머리가 그보다 가까우면 겹친다.

상한이 그 절반(**0.65sp**)을 넘으면 옆 음표를 잘못 집을 수 있다.
`0.5 < 0.65`이므로 0.15sp 여유가 있고, 후보가 둘 이상 나오는 것도 불가능하다
(두 후보가 다 범위 안이면 서로 1.0sp 이내인데, 최소 간격이 1.30sp다).

**아래에서 밀어 올리는 값**은 훨씬 작다. 300dpi 고정이므로 재실행 시 Δnx는 **0**이고,
알고리즘을 고쳐 좌표가 흔들려도 몇 px 수준(약 0.1sp)이다. 0.5는 그 5배다.

#### 실측 — 매칭 성공률

기준 짝을 매칭 규칙과 **독립적으로** 잡았다(정규화 좌표에서 상호 최근접).
성공률은 id 일치율이 아니라 **그 기준 짝을 몇 개나 맞게 붙였는가**로 잰다.

| 비교 | 기준 짝 | 맞게 붙음 | 틀리게 붙음 | 못 붙임 |
|---|---:|---:|---:|---:|
| **300 vs 300 (지원 범위)** | 240 | **240 (100%)** | **0** | **0** |
| 쇼팽 1쪽 300 vs 320dpi | 164 | 159 (97.0%) | 0 | 5 |
| 쇼팽 1쪽 300 vs 400dpi | 167 | 159 (95.2%) | 0 | 8 |
| 쇼팽 3쪽 300 vs 320dpi | 167 | 155 (92.8%) | 0 | 12 |
| 쇼팽 3쪽 300 vs 400dpi | 156 | 133 (85.3%) | **1** | 22 |
| 바흐 300 vs 320dpi | 139 | 115 (82.7%) | 0 | 24 |
| 바흐 300 vs 400dpi | 136 | 124 (91.2%) | 0 | 12 |

쇼팽 3쪽·바흐 세 쪽에서도 300 vs 300은 모두 **100% · 오매칭 0**이었다.

> **주의 — 상한을 0.6으로 올리면 표의 모든 칸이 100%가 된다. 그건 근거가 못 된다.**
> 기준 짝을 반경 0.6으로 정의했으므로 0.6 이상의 상한은 **자기 정의를 다시 확인하는 것**뿐이다.
> 해상도 간 진짜 성능은 이 방법으로는 잴 수 없다.

#### `step` ±1 2차 시도를 빼는 이유

처음에는 검출 y가 줄·칸 경계에 걸린 경우를 위해 2차 시도를 두려 했다. **재 보니 뺐다.**

1. **지원 범위 안에서 하는 일이 없다.** 300 vs 300에서 2차로 붙는 것은 **0건**이다
2. **해상도가 바뀐 경우에만 붙는데, 거기서 오매칭이 나왔다** (쇼팽 3쪽 300 vs 400, 1건)
3. **의미가 틀렸다.** 2차로 붙은 짝을 표본으로 보면 `D5 → C5`, `E5 → F5`처럼
   **음이 실제로 다르다.** 여기에 사용자가 고친 계이름을 얹으면 틀린 글자가 붙는다

즉 2차 시도는 **얻는 것이 0이고 잃을 것이 있다.** `step`이 다르면 `orphan`으로 넘긴다.

## 쓰는 법

결과 이미지를 만들 때 **라벨 목록도 항상 함께 저장한다.** 옵션으로 두면 정작
필요할 때 없다.

```
python main.py 악보.pdf
  -> output/악보_계이름.png
  -> output/악보_라벨.json      (--save-labels 로 경로 지정 가능)

python main.py 악보.pdf --relabel output/악보_라벨.json
  -> 인식을 건너뛰고 JSON만으로 다시 그린다
```

`--relabel`은 **JSON이 곧 그리는 내용**이다. 줄을 지우면 그 라벨이 빠지고,
`text`를 고치면 그대로 나온다. 사용자가 고친 것을 보존하는 것이 목적이다.

**검증: 저장한 목록을 그대로 다시 렌더링하면 원래 이미지와 픽셀 단위로 같다.**

| 악보 | 라벨 | 다른 픽셀 |
|---|---:|---:|
| 바흐 미뉴에트 | 185 | **0** |
| 쇼팽 D♭ 1쪽 | 240 | **0** |
| RE:Aoharu 1쪽 (PNG) | 226 | **0** |

읽기는 관대하다 — **모르는 필드는 무시하고**(앞으로 필드가 늘어도 옛 파일이 열린다),
**필수 필드가 없으면 몇 번째 라벨의 무엇이 없는지 말한다.**
`schema`가 이 프로그램이 아는 것보다 높으면 **열지 않는다.**

## 확신도 — 값 세 개, 실측으로 정했다

**JSON에는 값만 있다. 색과 형태는 렌더러가 정한다.** 앱과 데스크톱이 같은 값을
읽고 각자 자기 방식으로 그린다 — 표시 방식이 데이터에 섞이면 한쪽을 바꿀 때
다른 쪽이 깨진다.

| 값 | 뜻 | 근거 |
|---|---|---|
| `certain` | 걸린 신호가 없다. 그대로 믿어도 된다 | — |
| `caution` | **정밀도 낮은** 신호만 걸렸다. 아마 맞지만 확신은 못 한다 | `vertical_blocked` 정밀도 11% |
| `check` | **정밀도 높은** 신호가 걸렸다. 사람이 봐야 한다 | `weak_side_ink` 83% · `beam_adjacent` 100% |

**문자열이지 불리언이 아니다.** 네 번째 값이 생길 수 있기 때문이다.
읽는 쪽은 **모르는 값을 만나면 `certain`처럼 다루고 넘어간다** — 새 값이 생겼다고
옛 앱이 죽으면 안 된다.

### 실측 개수

`residual`을 등급에서 뺀 뒤의 값이다.

| 악보 | 라벨 | `certain` | `caution` | `check` |
|---|---:|---:|---:|---:|
| 쇼팽 D♭ 1쪽 | 240 | 210 (87.5%) | 23 | 7 |
| 바흐 미뉴에트 | 185 | 173 (93.5%) | 3 | 9 |
| RE:Aoharu 1쪽 | 226 | 225 (99.6%) | **1** | **0** |

`check` 개수가 **알려진 남은 유령 수와 맞는다** — 쇼팽 1쪽 7 대 5, 바흐 9 대 8,
**오류가 없는 RE:Aoharu는 0 대 0.**

### 「걸림 12」와 「걸림 16」 — 둘 다 맞다. 분모가 다르다

문서에 남은 실측표(`좌우잉크<0.40` **걸림 12** · 정밀도 83%)와, 나중에 같은 코드로
다시 센 값(**걸림 16**)이 안 맞아 보였다. **인식 코드는 그 사이 한 줄도 안 바뀌었다**
(`git diff 0d45b26 HEAD -- modules/`가 비어 있다). 원인은 측정 방법이었다.

앞의 측정은 **사람이 판정한 라벨만** 셌다.

```python
v = truth.get((d["x"], d["y"]), "")
if v in ("", "애매"): continue     # 사람이 판단 못 한 것은 뺀다
```

- 전체 라벨은 쇼팽 1쪽 240 + 바흐 185 = **425**
- 그중 사람이 `정상`/`유령`으로 판정한 것이 **418** (빈칸·`애매` 7개 제외)
- `좌우잉크<0.40`에 걸린 **16개** 중 **4개가 `애매`**였다 → 판정된 것만 세면 **12개**

**16 − 4 = 12. 두 값이 정확히 맞는다.**

| 판정 | 개수 | 어디 |
|---|---:|---|
| `유령(빔)` | **10** | 쇼팽 4 · 바흐 6 |
| `정상` | **2** | 쇼팽 x=1098 · x=2310 |
| `애매`(사람도 판단 못 함) | **4** | 쇼팽 x=1134 · 바흐 x=443·581·664 |

정밀도 83%(12건 중 10)는 **유효하다.** 표기에 분모만 빠져 있었으므로 여기 적어 둔다.

**`check`에 실제로 섞이는 진짜 음표는 2개다**(전체 425개 중 0.5%).
판별자를 억지로 만들지 않는다 — **유령을 `certain`으로 표시하는 쪽이 훨씬 나쁘다.**

### `snap_residual`을 등급에서 뺀 이유

처음에는 `caution`에 넣었다. 그러자 **오류가 하나도 없는 RE:Aoharu에서 표시가
10개** 나왔다. 빼니 1개다.

이 신호는 **정밀도 0%로 이미 기각된 것**이다(`docs/DECISIONS.md` 기각 목록).
잡는 유령이 0개인데 헛경고만 9개 늘렸다.

> **원칙으로 올렸다** — 기각된 신호를 '약한 신호'로 재활용하지 않는다.
> 정밀도 0%는 약한 게 아니라 **무관한** 것이다. (`docs/DECISIONS.md` §3-7)

### flags는 등급과 별개로 전부 남긴다

`confidence`가 `certain`이어도 걸린 신호가 있으면 `flags`에 남긴다.
`snap_residual`도 **기록은 계속 한다.**

기록과 등급은 다른 결정이다 — 기록은 나중에 유형별로 세기 위한 것이고
(`docs/DECISIONS.md` §3-6), 등급은 사용자에게 보여줄지 정하는 것이다.
앱이 나중에 다른 기준을 쓰고 싶으면 `flags`만 보고 자기 판단을 하면 된다.

flag 이름: `weak_side_ink` · `beam_adjacent` · `vertical_blocked` ·
`snap_residual` · `off_staff` · `no_ledger`

## 정하지 않은 것

- **여러 페이지를 한 파일에 담을지.** 지금은 페이지당 한 파일이다.
  앱에서 곡 단위로 묶어야 하면 바깥에 `pages: []`를 한 겹 두르면 된다 —
  `schema: 2`로 올리는 변경이다
- **음표 길이(리듬).** 지금 파이프라인이 분석하지 않는다. 나중에 넣으려면
  라벨에 `duration` 필드를 더한다. 없는 필드는 무시하는 것이 규칙이므로 호환된다
- **사용자 수정 이력.** `edited: true`만 있고 누가 언제 무엇을 고쳤는지는 없다.
  앱에서 되돌리기가 필요하면 그때 설계한다
