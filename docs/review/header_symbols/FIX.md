# 조표·박자표 위 계이름 — 수정 검증

2026-10-06 사용자 제보의 수정. `modules/clef_keysig.py`만 이번 오류에 한해 Codex가 고치도록 사용자 승인받았다. 소유권 규약 자체와 다른 인식 파일·정답 파일은 바꾸지 않았다.

## 원인과 변경

숫자 끝365를 이미 찾았지만, 첫 시스템 판별이 들여쓰기4sp에 묶여 실제1.7sp인 베토벤4중주를 놓쳤다. 밀도식은 좁은3/4 숫자를 넘지 못했고 최종 경계288에 조표·숫자가 남았다. GUI와CLI가 함께 쓰는 `analyze_staves`에서 고쳤다. 화면에서 check/caution을 숨기는 방법은 쓰지 않았다.

원본의 연속 세로줄로 첫 묶음을 확인하고, 뒤 묶음보다 음자리표 끝이 오른쪽이며 모든 보표가 동일한 박자표 끝을 직접 찾은 경우에만 그 끝을 공유한다. 이미 덮은 박자표 뒤에서 찾으면 실제 음표를 숫자로 오인하므로 검색은 음자리표 끝부터 한다. 같은 화음이 여러 성부에 반복되는 반례는 두 머리를 잇는 연속 기둥으로 제외한다. 형태 검사의 기존폭0.6~2.6sp·오차0.2sp·들여쓰기4sp·밀도값은 변경하지 않았다.

음자리표 검출 여부·종류·조표 판정은 바꾸지 않는다. 일부 음자리표를 놓쳐도 각 보표의 숫자가 같은 끝으로 직접 확인되면 경계만 공유한다. 연결선·일치가 확인되지 않으면 기존 경계를 보존한다. 이는 박자표 전체를 읽는 새OCR이 아니며 모든 조판·실제 사진의 기호 오인식이 없어졌다는 보장이 아니다.

## 재발 방지

`tests/test_header_symbols.py`는 run_all에 자동 포함된다. 수정 전 두 실제 조판과73px 이동 검사에서 실패한 로그, 재표본화 후보가 실패한 로그, 동일 화음 후보가 실패한 로그를 보존했다.

- Bravura·Leipzig 베토벤 첫4보표: 조표·3/4 기호 라벨 제거, 첫 실제 F4「파」 두 음표 유지. 뒤 묶음 비올라의 실제 음표·이음줄 경계 유지.
- 왼쪽 여백73px 추가: 경계도73px 이동. 제품 좌표 고정 필터가 아님을 확인.
- x0.25/0.5/0.75px, y0.5px, xy0.5px 실제 warpAffine: 숫자 영역이 다시 열리지 않고 첫 두 음표 머리를 보존.
- 이미 박자표를 덮은 Clara2: 다음 음표의 기둥·깃을 다시 검색해 삼키지 않음.
- 숫자 대신 같은9도 화음을 네 성부에 반복한 합성 반례: 경계가 화음 앞으로 유지.

## 대조 범위

전체 출력 수치는 `regression.json`, 사진 출력 수치는 `photo-regression.json`, 전체 검사 로그는 `run-all-final.log`에 보존한다. 같은 입력·설정으로 기준3827470의 헤더 함수와 최종 함수를 각각 실제 run_page에서 호출했다. 그 외 제품 함수는 현재 코드로 동일하게 유지한 대조다. 기준선 재사용 때 커밋·원본파일SHA·쪽 번호를 모두 확인했다. 골든이나selftest 기준은 갱신하지 않는다.

```powershell
python tools/check_header_symbols.py --check
python tools/measure_header_symbol_regression.py --extra-root <보지않은악보가있는체크아웃>
python tests/test_header_symbols.py
python tests/run_all.py
```

합성 사진은 기존 `generate_synthetic_photos.image_case`에서 세 원본(바흐/D♭/F조표)에 xy0.5px·회전0.5도·왼쪽그림자·흐림을 각각 적용한12장이다. 실제 촬영본 검증과 다르다. 원본이나 전체 원본 캡처는 커밋하지 않는다.
