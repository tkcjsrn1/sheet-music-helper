# PDF17 중 5쪽 GUI 지연 계측 (2026-10-13)

완료된 결과의 쪽 선택·예약 미리보기 갱신까지 **0.324~0.392초**. 이번 조건에서 완료 뒤 약1분 지연은 재현하지 못했다. 처리 중 다음 버튼 비활성은 관측했고, 이것을 실제 사용자 PC의 지연 원인 확정으로 해석하지 않는다.

## 방법과 원자료

소스 main `5b793aa` (#342 포함), 같은 PC CLI 측정 없는 시간에 실행했다. D♭1/6 · B♭m4 · Em1 · 바흐1을 원본 PDF에서 각 한 쪽 PDF로 복사한 뒤 내부 다중입력 작업자로 처리했다. 300dpi에서 원본 해당쪽과 복사한 입력의 픽셀은 5/5 완전히 같았다. 광학 입력은 같지만 원본 PDF의 전쪽 GUI 경로·합본 작성 방식과 동일한 실험은 아니다. 원본과 입력 해시는 원자료에 있다. 원본 악보/PDF/결과 악보 PNG는 커밋하지 않는다.

기존 `measure_gui_page_latency.py`의 함수를 재사용한다. 파일을 바꾸지 않고 측정용 함수에만 창 배치 대기/뷰포트 확인과 `update_idletasks`→`update`를 적용했다. 최초 반환시간 계측(0.21~0.26초)은 예약 fit/draw 완료를 포함하지 않아 `return_only.json.gz`로 구분한다. 그 뒤 창 배치가 미완료인 사본은 assert 실패했고 완료로 세지 않았다(`incomplete-layout.log`). 최종은 1117×713 캔버스와 fit/draw4회(최초표시+3전환)를 확인했다. 창은 입력 처리 전에 숨겼으며 실제exe/사람이 보는 첫 화면/하드웨어 페인트 검증이 아니다. 쪽 선택은 1·2쪽 사이3회씩이며 5쪽 모두 선택한 검사는 아니다.

최종 계측 실행61.574초 · 대조62.769초, 둘 다5쪽 성공. 계측/대조 PNG·JSON10파일 바이트 동일, 원자료에 SHA. 초기 반환시간 실행의 다른 처리 시간을 성능 개선으로 해석하지 않는다. 워밍업·캐시·PC 부하 변동이 있고 각 방식1회만 잰 값이다.

## 단계별 시간 (최종 계측, 초)
