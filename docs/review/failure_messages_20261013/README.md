# 실패 안내와 명시적 사진 재시도 (2026-10-13)

GUI 단일 입력·여러 이미지·여러 PDF쪽 오류를 같은 안내 함수로 설명한다. 인식·판정·문턱·파이프라인 순서는 바꾸지 않는다.

| 실제로 만든 입력 | 현재 실패/성공 | 안내 |
|---|---|---|
| 400×500 흰 이미지 | StaffNotFoundError | 악보 줄을 찾지 못함 + 원본 크기의 선명한 악보/사진 모드 제안 |
| 1×1 이미지 | cv2 resize의 `!dsize.empty()` | 이미지 크기 처리 실패 + 작은 조각 대신 원본 이미지 제안 |
| 손상 PNG | SheetMusicImageError | 파일 열기 확인/PNG·JPG로 다시 저장 |
| 암호 PDF | 실제 needs_pass=True | 비밀번호 해제 사본/이미지로 선택 |
| 합성 1° | 일반 모드 보정·보표6 성공 | 예전 「1°면 거부」 전제를 쓰지 않음 |
| 합성 4° | 일반 모드 StaffNotFoundError | 「사진 모드로 다시 시도해 보세요」 + 고정 버튼 |
| 같은 합성 4° | 버튼 클릭으로 photo=True, 실제 M1 보표6 성공 | 사용자가 누를 때만 재시도 |
| 위아래 기울기가 다른 합성 | PhotoRejectedError | 「스캐너·복사기·거치대로 정면에서 다시 찍어 주세요」, 재시도 루프 없음 |

1×1은 #333 이후 오선 단계 전 1/4 축소에서 실패했다. 새 크기 문턱을 만들지 않고 실제 resize 실패에 대한 안내만 붙였다. 비밀번호 안내는 PDF에 실제 암호가 있는 경우만 쓴다. 암호 없는 PDF의 같은 ValueError 문자열과 예상 밖 RuntimeError는 숨기지 않고 기존 진단을 남긴다. 보정 거부 후 조용히 원본으로 진행하는 경로는 없다.

## 검증

기능 부재 실제 red (실패2·오류2) → 실제 입력/버튼4검사 green. 기존 다쪽 실패 계속 처리 검사 유지. Aoharu1·D♭1·바흐1 기본 실제 GUI PNG/JSON6파일 바이트 동일 (`default_bytes.json`, #339 전 실제 출력과 대조). 합성 그림으로 오삭제나 사진 일반 지원을 보장하지 않는다.

`normal_refusal.png`, `photo_refusal.png`는 직접 생성한 입력을 소스 GUI에서 조작한 실제 1000×640 화면이다. 로그 위치로 스크롤했고, 재시도 버튼은 고정 영역이다. 캡처 배율은 변환 전에 맞췄으며 크기 검사를 통과한 최종 화면만 저장한다. 초기 200px/배율 오차 화면을 검증 화면으로 채택하지 않았다. exe 클릭 확인이 아니다. 원본 악보는 포함하지 않았다.

최종 전체 검사는 실제 종료를 확인한 뒤 추가한다. 새 베타는 #338·#340의 허용 범위 밖 슈베르트 기존행 변화 판단 대기로 중단한다.

최종 결과: **42/42 · 실패0 · 건너뜀0**, 골든711·현재 PDF17 일치. 최초 전체41/42의 실패1은 test_labels_cli의 화면 없는 호출에 새 버튼을 요구한 본인 회귀(하위오류2)였다. 버튼 초기화를 기존 결과 UI 초기화로 모아 기존 검사/기대값을 그대로22/22 통과했다. 새 안내4검사와 최종 코드의 기본3쪽PNG/JSON6파일도 다시 통과한 뒤 전체42개를 새로 완주했다. 최초 실패 로그는 성공 근거로 사용하지 않는다.
