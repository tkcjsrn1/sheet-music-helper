# N/P·F1 IME·NumLock 오류 — 2026-10-15

제품 수정 범위는 gui.py의 두 단축키 처리뿐이다. 인식·판정·골든·의존성 변경은 없다.

## 실제 기존 a9646b4 exe 진단

실제 GUI PID10316/부트18724, 14:00:27~14:04:55 KST(4분28초) 안에 진단하고 닫았다. 사용자 중단 전의 05시 소스 진단과 합쳐 하나의 연속15분 검사로 기록하지 않는다. 파일 해시는 기존 릴리스와 같고 새 exe를 만들지 않았다.

| IME | NumLock | 실제 기존 exe N/P | 실제 기존 exe F1 |
|---|---|---|---|
| 영문 | ON | 미통과: 0/2 유지 | 미통과 |
| 영문 | OFF | 통과: N→N→P, 1/2→2/2→1/2 | 도움말 표시 |
| 한글 | OFF | 미통과: 1/2 유지 | 도움말 표시 |
| 한글 | ON | 이번 기존 exe 진단에서는 별도 실행 안 함 | 별도 실행 안 함 |

[실제 입력·전면창·OS 포커스·IME](old-exe-events.jsonl). 기존 frozen exe에는 Tcl send가 없어 Tk 내부 위젯 이름은 직접 조회할 수 없었다. OS 창/PID와 소스 진단의 실제 Tk 포커스 기록을 구분한다. 최초 exe에 입력 경로를 전달한 시도는 GUI가 아니라 CLI였으므로 폐기했다. 다른 앱이 앞에 있던 입력은 소유권 검사로 차단했으며 성공에 넣지 않았다.

## 두 원인과 최소 수정

- Windows Tk event.state=8은 NumLock인데 기존 코드는 Alt로 취급했다. 실제 Alt 마스크0x20000/Ctrl4는 계속 차단한다. F1 바인딩 범위 문제는 아니었다.
- 한글 IME의 첫 물리 키는 keycode229 PROCESSKEY·빈문자로 온다. 나중에 완성되는 ㅜ/ㅔ를 매핑하면 즉시 이동하지 않고 중복 처리 위험도 있다. 이벤트 스레드 GetKeyboardState의 입력 큐에서 단일 N/P를 확인한다. 현재 순간의 GetAsyncKeyState로 바꾸지 않는다. 뒤늦은 조합 완료 문자는 무시한다.
- N을 누른 채 다른 키를 누르는 모호한 입력은 순회하지 않는다. 리뷰에서 발견한 이 반례는 [실패 재현](held-key-red.log) 뒤 고쳤다. 키 반복 속도에 따라 회귀 검사가 흔들리지 않도록 N down→M down/up→N up을 한 SendInput 배치로 보낸다.
- 입력칸의 N/P, Ctrl·Alt 조합은 기존처럼 순회하지 않는다. IME나 NumLock의 사용자 상태는 검사 뒤 복원한다.

단순 문자 매핑 후보의 실패와 최종 PROCESSKEY 실패 검사는 각각 [초기 RED](unit-red.log), [PROCESSKEY RED](process-unit-red.log)에 보존했다. 초기 후보가 단위 검사를 통과해도 실제 첫 한글 N에서 실패해 채택하지 않았다.
