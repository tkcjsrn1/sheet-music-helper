## 안전 장치와 확인

- `F:/akbo-data/HEAVY.lock`을 `open('x')`로 원자 취득하고 내용으로 소유권을 확인한 뒤 자기 잠금만 해제했다. CLI 잠금이 풀릴 때까지 대기했다. 임시 실행·그림·검사 사본은 `F:/akbo-data/tmp/codex-memory-20261023`에만 썼다.
- 각 작업 시작 전 **시스템 가용≥2.5GiB**, 커밋 여유≥3GiB. 실행 중 **가용<1GiB 또는 커밋 여유<2GiB**면 자기 Job만 종료한다. 0.2초 간격 감시이며 모든 순간의 시스템 안전을 보장하는 장치는 아니다. 본문 세 작업은 중단 기준 발동0.
- 32MiB씩 부모·자식에 할당한 작은 검사로 합산 계측을 확인했다. 별도로 실제 메모리를 고갈시키지 않고 읽는 값만 1GiB-1로 주입해 **본인 부모·자식 종료/종료코드77/잠금 해제**를 확인했다(`guard-check/checked.json`). 그 합성 최저값은 위 실측 표에 넣지 않았다.
- 첫 GUI 시도는 단일 선택 버튼(240,200)에 두 경로를 넣어 산출물0인 상태로 대기했다. 본인 검사 사본만 정상 종료 요청하고 실패를 보존했다(`first-gui-attempt`). 기존에 검증한 복수 선택 버튼(240,250)으로 계측 스크립트만 고쳐 재실행했다. 이 첫 값은 두 쪽 변환 최고치나 제품 결함의 근거로 쓰지 않는다.
- 모든 Job/검사 exe/자기 잠금을 정리했다. 입력 검사 IME 한글 상태 복원·NumLock ON 유지. 스피커 청취/SmartScreen은 이번에 검사하지 않았다.

## 원자료·재현 범위

`results.json`/`manifest.json`은 작업별 커밋·명령·시각·바이트 수치를 담는다. 각 작업 폴더의 `samples.jsonl.gz`와 `run.log.gz`, `workers-current.jsonl.gz`, 실행에 쓴 Windows 표준 라이브러리 계측기·작업별 스크립트·runtime 부트스트랩을 함께 보존했다. 입력 이미지·exe·ZIP은 커밋하지 않았다.

스크립트는 이 PC의 보존된 작업공간/기존 입력/기존 입력 보조에 의존하는 재현 기록이다. 새 실행은 이 기록 폴더가 아니라 저장소 밖의 **새 F:/akbo-data/tmp 하위 폴더**에 사본을 놓고 한다. 기존 결과를 덮어쓰거나 CLI 잠금을 무시하지 않는다. 첫 실행 `run.py check render exe full`은 첫 exe 시도 실패에서 멈췄다. `run.py exe-retry full`로 이어서 완료했고 `guard-check.py`도 통과했다. 중간 실패는 별도 보존했다.

관측한 입력과 실행 범위의 최고값이지 임의 악보/모든 설정의 상한이 아니다. 과거 로그는 시스템 가용량만 있어 과거 본인 프로세스 최고값을 복구할 수 없다. **이전 CLI 대기 프로세스 강제 종료의 원인은 미확정**이며, 이번 값만으로 원인을 부정하거나 메모리 문제가 해결됐다고 쓰지 않는다.
