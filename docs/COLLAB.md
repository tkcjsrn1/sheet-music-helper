# 협업 규약 — Claude Code + Codex

이 저장소는 **두 AI 에이전트가 번갈아** 작업한다.
가장 큰 위험은 버그가 아니라 **한쪽이 다른 쪽의 결정을 모르고 뒤집는 것**이다.
그러면 되돌리는 데 만든 시간보다 더 걸린다.

이 문서는 그걸 막기 위한 것이다. `AGENTS.md`(Codex)와 `CLAUDE.md`(Claude)는
모두 이 문서를 가리킨다.

---

## 0. 세 줄 요약

1. **자기 소유가 아닌 파일은 고치지 않는다.** 필요하면 소유자에게 넘긴다(§2).
2. **판정 조건과 문턱값은 측정 없이 바꾸지 않는다.** 바꾸려면 먼저 `docs/DECISIONS.md`를
   읽어라 — 대부분 이미 시도해서 기각된 것이다.
3. **작업 전후로 `python tests/run_all.py`를 돌린다.** **실패 0 · 건너뜀 0**이어야 커밋한다.

---

## 1. 왜 이런 규약이 필요한가

이 프로젝트의 핵심은 **광학 악보 인식의 판정 조건**이다. 코드는 짧은데, 그 안의
숫자 하나하나가 수백 개의 라벨을 사람이 눈으로 확인해서 나온 값이다.

`LEDGER_RUN_SP = 1.30` 은 한 줄이지만, 이 값은
음표 머리 폭 958개 실측 + 덧줄 있는 정상 음표 134개 + 덧줄 없는 유령 11개를
재서 나왔다. 코드만 보면 "1.3? 대충 1.5로 해도 되겠는데" 싶다. 실제로 그러면
**진짜 음표가 지워진다. 그리고 아무도 눈치채지 못한다.**

그래서 규칙은 하나로 요약된다 —
**측정으로 나온 값은 측정으로만 바꾼다.**

### 규약 문서 — 한쪽이 단독으로 고치지 않는다

`docs/COLLAB.md`(이 파일) · `AGENTS.md` · `CLAUDE.md`

이건 두 에이전트가 **지켜야 할 규칙 자체**다. 한쪽이 마음대로 고치면 규약이 아니다.
고칠 필요를 발견하면 `WORKLOG.md`에 제안을 남기고 **사람의 승인을 받는다.**
(모순이나 오류를 발견했을 때도 마찬가지다 — 지적은 하되 고치지 않는다)

### 공유

| 파일 | 규칙 |
|---|---|
| `WORKLOG.md` | 양쪽 다 쓴다. **추가만** 하고 남의 기록은 지우지 않는다 |
| `docs/TASKS.md` | **자기 절만** 고친다. 끝낸 항목은 지우고, 남의 절은 건드리지 않는다 |
| `docs/DECISIONS.md` | **Claude 전용.** 판정 조건의 채택·기각 기록이다 |

### 경계를 넘어야 할 때

고쳐야 하는데 남의 파일이면, **직접 고치지 말고 `WORKLOG.md`에 요청을 남겨라.**

```markdown
## 요청: [codex → claude] verify.drop_beam_ghosts 반환값
GUI에서 제외 사유별로 개수를 보여주고 싶은데 지금은 리스트만 옵니다.
reason별 카운트를 함께 주실 수 있나요? (급하지 않음)
```

## 3. 절대 규칙

### 3-1. 오삭제 0

**진짜 음표를 지우는 변경은 어떤 이유로도 머지하지 않는다.
사람의 승인으로도 통과시킬 수 없다.**

유령(없는 음이 하나 더 보임)은 사용자가 보고 넘어간다.
오삭제(있는 음이 사라짐)는 **알아챌 방법이 없다.** 둘은 대칭이 아니다.

오삭제를 발견하면 **작업을 중단하고 보고한다.** 승인을 구하는 것이 아니라,
그 방향이 틀렸다는 사실을 알리는 것이다. 실제로 그렇게 해서
'좌우 띠 비율' 방식을 통째로 버렸다(`docs/DECISIONS.md` 기각 3번).

의심스러우면 덜 지우는 쪽을 택한다.

### 3-2. 문턱값은 측정으로만

판정에 쓰는 숫자를 바꾸려면 **바꾸기 전에** 이걸 해야 한다:

1. `docs/DECISIONS.md`의 기각 목록에 있는지 확인 — 있으면 이미 실패한 방향이다
2. 최소 두 악보에서, 각 악보의 **여러 쪽**에서 잰다 (1쪽만 재면 안 된다 — §3-3)
3. 지울 후보를 전부 뽑아 눈으로 확인한다
4. 유도 근거를 코드 주석에 남긴다 — 어느 악보, 어느 쪽, 오선 간격 얼마

이걸 못 하면 그 변경은 하지 않는다. "더 깔끔해 보여서" 는 이유가 아니다.

### 3-3. 검증 단위는 '쪽'이다

두 악보에서 재도 부족하다. `docs/DECISIONS.md` 기각 3번을 보라 —
두 악보의 1쪽에서 양쪽 다 정밀도 100%·오삭제 0이었는데, 같은 악보 5쪽에서
진짜 음표 11개를 지웠다.

### 3-4. 골든은 신성하다

`tests/golden/*.tsv`의 라벨 711개는 사람이 원본과 한 마디씩 대조한 값이다.
**한 글자라도 달라지면 그 변경은 회귀다.**

정말로 의도한 개선이면:
1. 무엇이 왜 바뀌는지 `WORKLOG.md`에 먼저 적고
2. 바뀐 줄을 하나씩 확인한 뒤
3. `python tests/test_golden_regression.py --update`

`--update`를 "테스트가 빨개서" 돌리지 마라.

## 4. 작업 절차

### 시작할 때

```bash
git pull
python tests/run_all.py        # 시작점이 깨끗한지 확인
```

`run_all.py`가 **실패 0 · 건너뜀 0**이어야 한다. 하나라도 실패하거나 `[건너뜀]`이면
먼저 원인을 확인한다. `[건너뜀]`은 검증용 악보가 없다는 뜻이다 —
그 상태로는 안전장치가 절반만 작동하므로 그대로 진행하지 마라.

**테스트 개수는 기준이 아니다.** 테스트는 앞으로 늘어난다. 기준은 언제나
"실패 0 · 건너뜀 0"이지 "N개 통과"가 아니다. 문서에 개수를 적지 마라.

그리고 `WORKLOG.md` 맨 아래를 읽어라. 상대가 뭘 하다 멈췄는지 거기 있다.
할 일은 `docs/TASKS.md`에 소유권별로 적혀 있다.

### 브랜치

`main`에 직접 커밋하지 않는다.

```
claude/<주제>      예: claude/ledger-run-length
codex/<주제>       예: codex/gui-progress-bar
```

### 커밋은 알아서 한다 — 물어보지 않는다

**사용자에게 "커밋할까요?"라고 묻지 마라.** 아래 조건이 맞으면 그냥 커밋하고 푸시한다.

커밋하는 시점 — **검증이 통과한 논리 단위마다.** 세션 끝까지 모으지 않는다.

| 커밋한다 | 커밋하지 않는다 |
|---|---|
| `run_all.py`가 실패 0 · 건너뜀 0이고, 하나의 논리 단위가 끝났다 | 테스트가 실패하거나 `[건너뜀]`인 상태 |
| 문서·주석만 고쳤다 | 측정 중이라 결론이 안 난 중간 상태 |
| 측정 스크립트가 결과를 냈고 그 결과를 문서에 반영했다 | 실험용 스크래치 코드 (저장소 밖에 둔다) |

- 작업 브랜치(`claude/*`, `codex/*`)에 커밋하고 **푸시까지 자동으로** 한다
- `main`에는 직접 커밋하지 않는다. PR로 올린다
- 검증이 전부 통과하고 소유권을 넘지 않았으면 **PR 머지도 자동으로** 한다
- **예외 — 머지 전에 반드시 보고하고 승인을 받는 경우:**
  골든 라벨이 바뀌는 변경, 판정 문턱값 변경.
  되돌리기 어렵고 사용자가 알아채기 어렵다
- **승인 대상이 아닌 것 — 오삭제.** 오삭제가 하나라도 나오면 그건 승인을 구할 일이
  아니라 **중단할 일**이다(§3-1). 승인은 판단이 갈리는 것에 쓰고, 오삭제는 갈리지 않는다
- 승인을 받았다고 해서 **파일 소유권을 넘어갈 수 있는 것은 아니다.** 둘은 별개다

한 세션에서 여러 번 커밋해도 된다. 오히려 그게 낫다 — 어디서 깨졌는지 좁혀진다.

### 커밋 메시지

누가 했는지 접두사로 남긴다. 나중에 "이 값 누가 왜 바꿨지"를 추적할 수 있어야 한다.

```
[claude] 덧줄 검출을 수평 런 길이로 교체

좌우 띠 비율은 머리 중심 추정에 의존해 쇼팽 5쪽에서 정상 음표 11개를
지웠다. 덧줄은 수평선이므로 그 y에서 런 길이를 잰다.
문턱 1.30sp: 머리 폭 실측(봉우리 1.2sp)보다 넓고, 정상 최소 1.40sp와
유령 최대 1.19sp 사이.

측정: 쇼팽 6쪽 + 바흐 1쪽, 90개 제거, 전부 육안 확인, 오삭제 0
```

### 끝낼 때

`WORKLOG.md`는 **커밋에 포함시킨다.** 푸시한 뒤에 쓰면 그 기록이 어디에도 남지 않는다.
순서는 이렇다:

```bash
python tests/run_all.py                    # 실패 0 · 건너뜀 0
# WORKLOG.md 에 항목 추가 (§5)
git add -A && git commit -m "[claude] ..."  # WORKLOG 갱신이 이 커밋에 함께 들어간다
git push -u origin <브랜치>
```

세션에서 커밋을 여러 번 했다면 `WORKLOG.md`는 **마지막 커밋에 한 번만** 넣는다.
커밋마다 로그를 고치면 충돌만 는다.

- 쇼팽 6쪽 + 바흐, 90개 제거, 전부 육안 확인, 오삭제 0

**남긴 것**
- 쇼팽 2~6쪽 표본 판정 미완. 격자는 `debug/sample/`에 생성됨

## 7. 자주 하는 실수

| 하려던 것 | 왜 안 되는지 |
|---|---|
| "문턱값이 어중간하니 반올림하자" | 그 어중간한 값이 두 분포 사이의 유일한 지점이다. `docs/DECISIONS.md` §1 |
| "좌우 띠에서 각각 잉크 비율을 재자" | 이미 해봤고 진짜 음표 11개를 지웠다. 띠 위치가 머리 중심 추정에 매달려 있다. 기각 3번 |
| "그럼 좌우 중 큰 쪽만 보면 되겠네" | 그것도 해봤다. 오삭제는 0이었지만 문턱 여유가 0이라 버렸다. 기각 4번 |
