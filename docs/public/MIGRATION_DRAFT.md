# 새 공개용 저장소 이관 절차 초안

**실행 승인 전이며 명령을 실행하지 않았다.** 기존 private 저장소는 이력·검증 자료와 함께 보존한다. force push·filter-repo·BFG·과거 파일 삭제로 해결하는 안은 이번 범위가 아니다. 공개 여부는 사용자가 정한다.

1. 공개 후보의 정확한 커밋과 코드/자료 책임자를 정한다. 별도 빈 작업 폴더에 허용 목록으로 복사할 파일을 검토한다. 기존 `.git`·refs·원격·stash는 복사하지 않는다. 새 저장소도 먼저 private staging으로 만든다.
2. 코드·빌드 설정·의존성 고지·일반 사용 문서만 우선 허용한다. 원본/파생 악보, docs/releases·docs/review의 그림, inputs·output·dist·debug, 신고 ZIP, 설정/개인 경로, 내부 WORKLOG·원자료·이 목록 자체는 기본 제외한다. 아이콘도 출처 확인 전 보류한다. 확장자 차단만으로 판단하지 말고 실제 복사 명세를 검토한다.
3. 검증용 골든/픽스처는 원본·정답 권리까지 확인한 뒤 **별도 승인**한다. 기존 골든711·PDF17을 지우거나 쉬운 합성 데이터로 바꾸어 동등 검증이라고 하지 않는다. 공개 코드만으로 가능한 단위 검사와 private 악보가 필요한 전체 검사를 문서에서 구분한다. 공개 CI에서 자료가 없어 건너뛰면 미검증으로 적는다.
4. 새 staging의 최초 커밋 전 파일 목록·바이너리/아카이브 내부·문서 URL/경로·개인정보·비밀을 별도 점검한다. 신고 자료를 예시로 넣지 않는다. 허용된 자체 합성 예시와 출처/생성기를 넣고 다른 원본이 섞이지 않았는지 확인한다. 이 작업은 이번에 실행하지 않았다.
5. 라이브러리·동봉 폰트의 **해당 버전** 고지와 실제 exe archive 목록을 대조한다. PyMuPDF는 현재 exe 제외를 유지한다. 소스 PDF 경로를 공개/배포할 때의 라이선스 선택은 따로 결정한다. [현재 남은 고지 문제](LICENSE_INVENTORY.md)를 먼저 정리한다.
6. 코드 사본이 원 후보와 같은지 해시로 확인하고, 기존 private 검증 환경에서 전체/골든/PDF/strict/소스-exe·실입력 검증을 한다. 공개 staging에서도 이용 가능한 검사와 문서의 실행 절차를 확인한다. 두 환경의 성공을 혼동하지 않는다.
7. 사용자가 문서·라이선스·샘플·확인 항목을 승인하면 그때 public 전환과 릴리스 업로드를 별도 수행한다. exe/ZIP은 Git 소스 이력에 넣지 않고 승인된 릴리스 첨부로만 다룬다. SHA256·빌드 커밋·고지·알려진 한계를 함께 제공한다.

완료 조건은 저장소가 새 것이라는 사실이 아니라 **검토한 허용 목록 외 자료0, 확인 가능한 출처/고지, 재현 가능한 빌드·검증, 사용자 공개 승인**이다. 이번 결과는 이 절차 초안과 목록뿐이다.
