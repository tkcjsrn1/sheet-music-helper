### 잉크·덧줄·기둥을 피하는 방식

- `gray<128`을 잉크로 잡고 적분영상으로 상자 안 잉크량을 센다. 음표 머리는 입력 음표 중심의 가로±0.62sp·세로±0.48sp 사각형으로 따로 막는다. 이것은 실제 머리 윤곽 분할 결과가 아니다.
- 오선의 `line_ys` 주변 행(반올림 위치 기준 -1~+1)을 장애물 마스크에서 지운다. 다른 보표 오선까지 가로지르는 수는 별도로 센다.
- **덧줄 전체를 찾아 지우는 코드는 없다.** 주석의 「오선·덧줄은 뺐다」라는 표현과 달리 이 함수가 실제로 지우는 것은 `line_ys` 행이다. 덧줄·기둥·빔·붙임줄·손가락 번호·셈여림 등은 일반 잉크로 남는다. 글리프 종류를 구분해서 피하지 않는다.
- 마디선은 오선 행을 지우기 전에 `verify.barline_positions`를 읽기 호출한다. 라벨 중심과 음표 중심 사이에 마디선이 있으면 후보를 제외한다. 글자 상자의 가장자리가 마디선에 걸리는 것까지 금지하는 규칙은 아니다. 예외가 나면 빈 마디선 목록으로 진행한다.
- 흰 테두리 `max(2,round(font_px*.11))`와 pad2, check 추가 여백2가 충돌 상자 크기에 들어간다. caution은 색만 달라져 추가 여백이 없지만 check는 후보와 `row_step`까지 달라질 수 있다.
- 기존 x 이탈 경고는 의도한 `x_shift`를 빼고 판단한다. **그 경고0으로 실제 최종 가로 이동이 작다고 증명할 수 없다.** 반환 `gap`도 세로 간격만 기록하므로 실제 dx나 2차원 거리가 아니다.

## 5. 고칠 방향 — 아직 채택/구현하지 않은 안

1. **규칙의 우선순위부터 정한다.** 어느 음표의 라벨인지, 화음의 음높이 순서, 머리·임시표 가림 방지를 먼저 유지한다. 다음에 반복 구간의 같은 방향/간격과 한 화음의 공통 열을 선호한다. 단순히 모든 라벨을 같은 절대 y에 놓으면 원음과의 연결을 잃을 수 있다.
2. **단선율과 밀집 화음을 분리해 비교한다.** 단선율은 근처 음형/마디 안에서 방향과 간격이 안정되도록, 화음은 하나의 묶음에서 공통 앵커와 위→아래 순서가 읽히도록 후보를 비교한다. 음표와 가까운 일관성/보표 밖 공통 줄 방식의 실제 전후 그림을 먼저 보고 선택한다. 그룹 판정을 위해 인식 코드를 바꾸지 않는다.
3. **순차 탐색의 영향부터 확인한다.** 앞 라벨·중복 좌표·한 글자/여러 글자·check 여백 때문에 어느 분기에서 벗어나는지 나중에 진단 자료로 확인한다. 위치 점수와 후보 구성의 변화를 각각 대조하고 여러 상수를 한꺼번에 바꾸지 않는다.
4. **기각8의 반례를 유지한다.** 가로 이동을 무조건 줄이거나, 최대 이동을 줄이고 남은 라벨을 숨기는 해결은 하지 않는다. 단순한 방향 고정도 겹침/머리 가림/다른 마디로 이동하는 경우를 먼저 확인한다.
5. **확신도와 인식 오류를 배치로 덮지 않는다.** 점선을 없애거나 글꼴을 최소16px 아래로 줄여 혼잡만 줄이지 않는다. 유령 삭제·음고 변경은 이 작업 범위가 아니다. 긴 bb/## 라벨이 들어오는 다음 베타의 고정 입력도 별도로 필요하다.

## 6. 전후 비교 방법 — 다음 구현 단계에서 실행할 계획

### 6-1. 기준을 먼저 고정

- 이번 조사에서 본 PNG와 다음 베타 결과를 별도 보관한다. 같은 renderer라도 라벨 집합·확신도·구간 조표가 달라지므로 두 빌드를 배치만의 대조군으로 바로 쓰지 않는다.
- 같은 원본 이미지 바이트, 같은 라벨 JSON(사용자 수정/구간 조표/겹임시표 포함), 같은 보표/글꼴 파일/설정/확신도를 고정한다. 기존 JSON 재렌더 경로로 **현 renderer가 해당 기준 PNG를 먼저 정확히 재현**하는지 확인한다. 불일치하면 헤더·범례·설정·후처리를 먼저 추적한다.
- 그 뒤 renderer 사본에서 배치 변경 하나씩 비교한다. 재인식해서 얻은 다른 라벨 목록을 전후 비교에 섞지 않는다. 이번에는 이 작업을 실행하지 않았다.

### 6-2. 가독성과 안전을 따로 비교

- 같은 배율의 전/후 국소 그림을 A~G 구간과 평범한 대조 구간에 함께 둔다. 보기 좋은 일부 구간만 선택하지 않는다.
- 나중에 반환 placements에서 **음표 중심↔글자 상자 중심 실제 dx/sp**, 세로 gap/sp, 같은 상황의 방향 전환, 화음 열의 가로 편차와 음높이 순서, 처음/예비/최후 위치 선택을 따로 기록한다. 기존 x 경고·gap 하나로 대신하지 않는다. 어떤 경우를 같은 상황으로 묶었는지도 보표·음형·화음·등급·폭 등으로 명시한다.
- 겹침은 글자 bbox, 흰 테두리, 점선 포함 상자, 실제 글자 획 교차를 구분한다. 마디선도 중심 사이 넘김과 상자 가장자리 걸침을 구분한다. 머리 가림·임시표/손가락 번호 등 원본 기호 가림을 별도로 눈으로 본다.
- 기존 [golden 배치 검사](../tests/test_golden_regression.py)는 글자 bbox 중심의 지표이며 analyze 경로가 실제 제품 경로와 다르다. 확신도 인자를 주지 않는 호출도 있어 check 여백을 실제 제품처럼 검사한다고 단정할 수 없다. 그 파일을 수정하지 않고, 별도 Codex 검증에서 **제품과 같은 JSON/인자**로 배치한다.
- 예전 gap>30px와 현재 gap>3sp를 섞지 않는다. 기존 지표는 회귀 대조로 보존하고 새 일관성 지표는 새로 정의한다. 목표 수치는 이번 조사에서 임의로 정하지 않는다.
- Aoharu 3쪽·PDF17 같은 기존 범위뿐 아니라 작은 sp, 밀집 화음, 2도 화음, 보표 사이, 덧줄/기둥, 긴 표기(bb/##), check와 일반 혼재, 동일 좌표 중복, 그림 가장자리/마디선, 가능한 경우 기존 M1 통과 파생 입력을 포함한다. 새 렌더/측정은 빌드 보고 뒤 단독 시간에 한다.

## 7. 인식 데이터 불변 검증

- renderer만 바꾸는 대조는 문서를 읽은 직후/렌더 후 파일 전체 바이트·해시를 비교한다. JSON을 다시 만드는 것으로 우회하지 않는다. `labels[].x/y`는 원음표 좌표이고 placements의 x/y는 화면 글자 상자이므로 두 좌표를 혼동해 JSON에 덮어쓰지 않는다.
- 문서 객체도 전후 깊은 복사와 비교해 schema/source/music/staves, label 순서·중복 수·ID·원음표 좌표·pitch/accidental/text/confidence/flags/key·사용자 수정 이력을 보존한다. 순서 없는 set이나 개수만 비교해 중복 라벨 교환을 놓치지 않는다. 전달된 note 객체·순서도 바뀌지 않아야 한다.
- 이후 제품 변환 경로에서는 같은 소스/입력/설정에서 배치 변경 전후의 JSON 바이트가 같아야 한다. 예상되는 차이는 결과 PNG와 렌더링 placements뿐이다. 머리말·범례의 별도 그리기 정책을 의도치 않게 바꾸지 않는다.
- 정답711과 PDF17 라벨·조표·음자리표 및 전체 검사 실패0·건너뜀0을 확인한다. 골든/스냅샷을 이 작업에 맞춰 갱신하지 않는다. 저장/재열기, 편집/삭제/추가/되돌리기, 쪽 전환, 영역 선택, 검토 순회/클릭·강조가 새 placements를 같은 라벨에 대응시키는지도 검사한다. 화면 클릭 처리가 placements를 소비하기 때문이다.
- **PNG 바이트 불변을 요구하지 않는다.** 배치 개선은 의도적으로 픽셀이 달라지는 작업이다. 대신 새 가림/겹침/순서 역전/라벨 누락을 별도로 확인한다.

## 8. 남은 것 / 아직 하지 않은 것

- PNG의 각 관찰을 최종 note/label 번호와 연결하고 실제 선택 분기까지 추적하는 작업. 현재 그림만으로 개별 이동 원인은 확정하지 않았다.
- 원자료가 확인되지 않은 상수의 과거 근거 추적, 대상 범위/공통 배치 기준선의 비교안과 사용자 화면 판정.
- 이 배치 조사에는 코드 변경·새 배치 렌더·새 배치 측정이 없다. 별도 e141908 베타 검증은 #401 기록과 구분한다. 원본 PNG와 기존 제품/판정/골든/규약은 수정하지 않았다.
- e141908 베타 보고 뒤 사용자 지시로 건반·연습 목표와 함께 문서 PR로 올린다. 다음 단계는 고정 JSON으로 배치 전후 비교안을 만드는 것이며 이번에는 구현하지 않는다.
